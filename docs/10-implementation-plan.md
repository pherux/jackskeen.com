# Implementation Foundation Plan

## Current state

The repository originally contained documentation only. The application foundation now uses npm, Next.js App Router, strict TypeScript, Tailwind CSS, shadcn/ui, ESLint, and Prettier. The only rendered route is an explicitly marked, noindex placeholder required for a valid Next.js build; no marketing UI or approved content has been implemented.

## Proposed project structure

```text
src/
├── app/                    # Routes, metadata files, route handlers, error states
├── components/
│   ├── layout/             # Header, navigation, footer
│   ├── sections/           # Reusable editorial/marketing sections
│   ├── content/            # Article, podcast, video, and rich-text rendering
│   ├── forms/              # Form UI and states
│   ├── seo/                # Breadcrumb and JSON-LD presentation helpers
│   └── ui/                 # Owned shadcn primitives
├── hooks/                  # Browser-only reusable behavior
├── lib/
│   ├── sanity/             # Clients, typed queries, image helpers, preview logic
│   ├── seo/                # Metadata, canonical, schema, and sitemap utilities
│   ├── analytics/          # Consent-aware analytics helpers
│   └── redirects/          # Redirect lookup and validation
├── styles/                 # Shared design-system CSS beyond app globals
└── types/                  # Cross-cutting application types

sanity/
├── schemaTypes/            # CMS models and validation
└── structure/              # Editorial Studio structure

scripts/
└── migration/              # WordPress inventory, transform, import, and QA tools
```

Route groups may organize marketing and editorial routes without changing public URLs. Explicit strategic routes must take precedence over the legacy root-level article route, and the migration inventory must detect collisions with reserved slugs before that legacy route is added.

## Major dependencies

Installed foundation dependencies are Next.js, React, Tailwind CSS, shadcn/ui with Radix primitives, and the small class-composition utilities generated by shadcn. ESLint, TypeScript, and Prettier are development dependencies.

Add dependencies only with the feature that needs them. The anticipated CMS set is `sanity`, `next-sanity`, `@portabletext/react`, and Sanity image tooling. Forms will likely use a schema validator, while tests will add Vitest and Playwright. Analytics, CRM, scheduling, consent, and spam-protection packages must wait for integration decisions.

## CMS integration approach

Keep Sanity schemas and Studio structure separate from React presentation. Create one server-only client for published content and a token-protected preview client for Draft Mode. Keep GROQ queries by content domain, generate or validate TypeScript result types, and map CMS documents into presentation-friendly data at the server boundary. Use Sanity webhooks to revalidate tagged content after publish.

The Sanity project, dataset, Studio deployment location, API version policy, and redirect ownership must be confirmed before CMS implementation. Testimonials require an approval-status validation rule and must never be queryable as public proof until approved.

## Rendering strategy

Use React Server Components and the Node.js runtime by default. Pre-render marketing, article, topic, podcast, video, book, and success-story pages; revalidate them from Sanity publish events. Use Client Components only for interaction such as menus, accordions, forms, media controls, and analytics listeners. Use Server Actions for internal form mutations and Route Handlers for external webhooks or integration endpoints. Draft Mode is dynamic and must remain noindex.

## SEO architecture

Use a shared metadata builder around the Next.js Metadata API with a confirmed canonical origin, per-document overrides, self-canonicals, Open Graph data, and explicit robots behavior. Generate sitemap and robots routes from canonical, indexable content only. Keep JSON-LD builders typed and colocated in `lib/seo`, and render schema only from visible, verified CMS fields. Preserve valuable root-level legacy URLs, keep redirect sources out of sitemaps, and test redirect chains and canonical collisions.

## Migration tooling approach

Build an idempotent TypeScript CLI under `scripts/migration` that ingests WordPress XML/API exports and a URL inventory. Separate extraction, normalization, HTML/shortcode-to-Portable-Text transformation, media import, topic mapping, Sanity writes, and reporting. Support dry runs, stable document IDs, resumable image imports, structured error logs, and machine-readable QA reports. Preserve original dates, authorship, canonicals, slugs, captions, and useful alt text. Do not place production exports or secrets in version control.

## Testing strategy

Keep the mandatory checks as formatting, ESLint, strict TypeScript, and a production build. Add unit tests for URL, canonical, schema, redirect, and migration transforms; component accessibility tests for interactive primitives; and Playwright coverage for the critical journeys listed in the requirements. Add route/link smoke tests, representative responsive checks at the required widths, structured-data validation, and production Lighthouse checks for key templates.

## Open decisions and blockers

- Confirm Sanity, provision its project/dataset, and decide whether Studio is embedded or separately deployed.
- Confirm the Vercel project, environments, canonical host, and preview-domain indexation policy.
- Confirm the primary CTA destination and the Kit/CRM/Calendly, newsletter, spam-protection, consent, and analytics workflows.
- Complete the existing-site crawl, WordPress/media exports, URL migration inventory, redirect inventory, and search/backlink baseline.
- Resolve whether `jackskeenlive.com` content and offers consolidate into this site.
- Approve sitemap consolidation, positioning, content briefs, proof, legal copy, photography, typography, colors, tokens, and motion rules.
- Decide whether migration redirects must be literal HTTP 301 responses. Next.js/Vercel commonly use HTTP 308 for permanent redirects, while the migration document explicitly requests 301.
- Decide whether redirects are source-controlled, CMS-managed, or split between a static high-priority map and a scalable lookup service.
- Define the search/discovery crawler policy separately from model-training crawler permissions.

These items block CMS/data modeling, migration freeze, production SEO, forms, analytics, or final visual work; they do not block the local application foundation.

## Toolchain compatibility note

Next.js 16.3.3's current lint stack does not yet run correctly on ESLint 10 because an upstream React lint plugin still uses the ESLint 9 rule context API. The foundation therefore pins ESLint 9.39.5, matching the official Next.js scaffold, until the Next.js lint dependency chain supports ESLint 10. This does not block linting or builds, but npm reports the ESLint 9 release line as unsupported.
